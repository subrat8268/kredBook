# UX & Product Audit — 2026-06-13

**Audience:** Indian SME vendors (kirana stores, wholesalers, small traders)  
**Devices:** Low-end Android (Redmi, Realme), semi-literate users, Hindi/regional languages  
**Scope:** Core screens — Dashboard (route + component), People list, Customer Detail, Entry list, Payment flow, share templates, feedback components, offline handling

## 5. Transaction Filter Tabs

### ⚠️ Minor — Scroll position not reset on tab switch
- **File:** `CustomerDetailScreen` → `txFilter` state change → `setHistoryExpanded(false)`  
- **Issue:** When switching filter tabs, `historyExpanded` resets to `false` (collapses list), but the **parent `ScrollView` scroll position is NOT reset** (no `scrollViewRef` is passed to it).  
- **User impact:** Low for typical lists — collapsing the list auto-reduces height so the empty space is less visible. Could confuse users with very tall initial transaction lists.  
- **Fix:** On `txFilter` change, call `scrollViewRef.current?.scrollTo({ y: 0 })`.

### ⚠️ Minor — Filter chip accessibility
- **File:** `CustomerTransactionTabs.tsx`  
- **Issue:** Filter chips (All/Entries/Payments) likely use `paddingVertical: spacing.xs` which may be <44pt touch target.  
- **User impact:** Hard to tap accurately on low-end touchscreens with less precision.  
- **Fix:** Ensure `minHeight: 44` on each chip.

## 6. Payment Flow Step Count & Keyboard Behavior

### ✅ Good — Step count (3 stages: form → confirmed/queued → done/share)

- `ModalStage = "form" | "confirmed" | "queued"` with clear transitions.

- **User impact:** Confusing — user enters ₹5000 on ₹2000 balance, button stays disabled, no error shown.  
- **Fix:** Show inline warning: "Amount exceeds balance due (₹2,000)" below the input.

## 7. "View Older History" Behavior

### ⚠️ Blocker — Loads ALL remaining transactions at once
- **File:** `CustomerDetailScreen` → `setHistoryExpanded(true)`  
- **Issue:** `onChangeFilter` resets `historyExpanded` to false. When expanded, **all** remaining items render at once in `FlashList`. A customer with 200+ transactions causes 185+ items to render simultaneously. FlashList has `scrollEnabled={false}` (embedded in ScrollView) — so it can't virtualize.  
- **User impact:** Severe performance degradation on low-end Android (jank, delayed tap response, possible ANR). For power users (wholesalers) with hundreds of entries per customer, this is a **daily pain point**.  
- **Fix:**  
  1. Remove `scrollEnabled={false}` or untangle from ScrollView  
  2. Paginate "View Older" — load 20 at a time, show "Load 20 more" button  
  3. Show loading spinner during expansion

### ⚠️ Minor — No loading indicator during expansion
- When user taps "View Older History (XX more)", there's no visual feedback between tap and render.  
- **Fix:** Show a brief loading/activity indicator in the button or below it during state update.

## 9. WhatsApp / Share Messaging

### ⚠️ Major — Inconsistent currency symbol in WhatsApp messages
- **File:** `src/utils/shareTemplates.ts` — Uses `formatINR()` which includes `₹` symbol.  
- **File:** `usePersonDetail.onWhatsApp()` in `usePeople.ts` — Hardcodes `Rs. {netBalance}` (uses `Rs.` not `₹`).  
- **User impact:** Inconsistent — header share uses `₹` (through `formatINR`), while on WhatsApp action uses `Rs.`. This confuses semi-literate users who may think amounts differ.  
- **Fix:** `usePersonDetail.onWhatsApp()` should use `formatINR()` consistently instead of `Rs.` prefix.

### ⚠️ Minor — Hindi share messages use `₹` indirectly via `formatINR()`
- The `buildPaymentShareMessage` and `buildLedgerShareMessage` in `shareTemplates.ts` use `formatINR()` which outputs `₹`. This is fine for Hindi users too, but worth noting the template messages are well-localized.

### ✅ Good — Payment receipt share uses `buildPaymentShareMessage`
- Properly localized, includes customer name, amount, date, remaining balance, business name.

### 🆕 Major — `onWhatsApp` sends unformatted `netBalance` with decimals and no zero guard
- **File:** `usePeople.ts` → `usePersonDetail.onWhatsApp()`  
- **Issue 1 (formatting):** `netBalance` is a raw number (`customer?.outstandingBalance ?? 0`, `Math.round(...*100)/100`). The WhatsApp message template is:
  ```
  Dear {name}, your outstanding balance with {biz} is Rs. {netBalance}.
  ```
  This outputs `Rs. 12547.5` (no comma formatting, uses `Rs.` not `₹`, shows unwanted decimals). The correct value reference is `formatINR(netBalance)`.
- **Issue 2 (zero guard):** No check for `netBalance <= 0`. A vendor could send `Rs. 0 – please pay` to a settled customer — a real user complaint waiting to happen.  
- **Fix:** Guard: `if (netBalance <= 0) return` or show alert "No outstanding balance to share". Use `formatINR(netBalance)` in the template.

### 🆕 Minor — `onWhatsApp` swallows all errors silently
- **File:** `usePeople.ts` → `usePersonDetail.onWhatsApp()`  
- **Issue:** The `catch` block handles only "WhatsApp not installed" (`Alert.alert("Cannot open WhatsApp", ...)`). If `Linking.openURL` fails for another reason (invalid URL from bad phone number, malformed URI), the error is silently swallowed — user sees nothing.  
- **Fix:** Use a generic fallback message in the catch block if error is not specifically about WhatsApp missing, e.g., "Could not open WhatsApp. Please try again."

### ⚠️ Minor — Filter chips may be undersized
- **File:** `CustomerTransactionTabs.tsx` — `paddingVertical: spacing.xs` likely <44pt.

### ✅ Good — Transaction rows: `p-4` (16px padding × 2 = ~56pt height)
- **File:** `CustomerTransactionRow.tsx` — Adequate.

### ⚠️ Polish — No `accessibilityLabel` on transaction rows
- **File:** `CustomerTransactionRow.tsx` — Pressable has no `accessibilityLabel` or `accessibilityRole`.  
- **Fix:** Add `accessibilityRole="button"` and `accessibilityLabel` describing the transaction.

### ✅ Good — Dashboard "See all" has `accessibilityLabel`
- **File:** `DashboardFollowUpSection.tsx` line 43 — `accessibilityLabel={`See all ${overdueTotalCount} overdue customers`}`.

### ⚠️ Major — ErrorState has poor contrast and no retry
- **File:** `ErrorState.tsx` — Red text on default background. On low-end screens with lower contrast or in sunlight, red-on-default may fail WCAG AA contrast (3:1 minimum for large text).  
- **Fix:** Add a light red background container, ensure text color meets 4.5:1 contrast ratio. Add optional `onRetry` prop.
