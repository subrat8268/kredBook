## 🔴 Critical

### C1 · Error banner flash on mount
**File:** `login.tsx:138–157`

Both mutations (`loginMutation`, `googleSignIn`) are initialized with `isIdle: true`. On first render, neither `isError` is true, so the banner is hidden — correct. However, if either mutation was previously reset and retains stale `isError`, the banner would flash. This is a React Query edge case, not a runtime crash, but a guard like `isSubmitted` or checking `attempts > 0` would harden it.

**Fix:** Add a local `submittedRef` that tracks whether the user has actually submitted the form. Only show error banner when `submittedRef.current` is true.

---

### C2 · Both buttons disabled simultaneously blocks all actions
**File:** `login.tsx:123,131`

`Button` sets `disabled` when `loginMutation.isPending` (line 123). `GoogleButton` also sets `disabled` when `loginMutation.isPending` (line 131). This means while Google is signing in, the Sign In button is not disabled — but while Sign In is pending, both buttons are disabled.

The opposite direction is unprotected: if `googleSignIn.isPending`, the `Button` Sign In remains tappable. Two simultaneous auth flows could race.

**Fix:** Add `disabled={googleSignIn.isPending}` to the Sign In `Button`'s `disabled` prop (line 123).

---

### C3 · No screens doc exists for Login
**File:** `docs/screens/` (missing)

`docs/screens/login.md` does not exist. Only `docs/flows/login.md` exists. The Phase 4 mandatory redesign routine requires a screen doc. This must be created before 4.3.2b.

**Fix:** Create `docs/screens/login.md` from `docs/flows/login.md` plus audit findings.

## ⚠ High

### H1 · `as any` casts on navigation
**File:** `login.tsx:111,160`

```tsx
router.push("/(auth)/resetPassword" as any)
router.push("/(auth)/signup" as any)
```

Expo Router's `router.push` accepts `Href` type, not raw strings. These `as any` casts bypass type checking — if route paths change, there's no compile-time error.

**Fix:** Use typed `Href` or wrap in a typed constant: `const Routes = { reset: "/(auth)/resetPassword" as const, signup: "/(auth)/signup" as const }`.

### H2 · `as any` casts on error access
**File:** `login.tsx:153–154`

```tsx
(loginMutation.error as any)?.message ??
(googleSignIn.error as any)?.message ??
```

React Query's `error` is typed `Error | null`. Accessing `.message` is safe without `as any`.

**Fix:** Remove `as any` — `loginMutation.error?.message` works directly.

### H3 · Subtitle mismatch — flow doc vs implementation
**File:** `docs/flows/login.md:16`

Flow doc says: `"Sign in to your kredBook"`  
Code has: `"Sign in to continue tracking customers, entries, and payments"`

Both are valid, but the doc must match implementation.

**Fix:** Update `docs/flows/login.md` subtitle to match code, or vice-versa.

### H4 · AuthCard shadow source uses `colors.textPrimary`
**File:** `src/components/ui/AuthCard.tsx:14`

```tsx
shadowColor: colors.textPrimary,
```

In dark mode `textPrimary` is `#F1F5F9` (near-white). This creates a light-colored shadow on a dark surface card, which might look unusual. The intent was likely `colors.ink` (black-based) with very low opacity.

**Fix:** Use `colors.ink` with `shadowOpacity: 0.04` — or use `colors.surfaceAlt` / `colors.border` for a subtle shadow that works in both modes.

### H5 · `hasSeenWelcome` set in two places — potential stale state
**Files:** `app/index.tsx:35` (welcome screen), `src/hooks/useAuth.ts:61` (login mutation)

The welcome screen sets `hasSeenWelcome = "true"` when navigating to signup. The login mutation also sets it on success. If a user opens the app, goes to login, then closes before signing in, `hasSeenWelcome` is not set — next launch still shows welcome. That's correct.

But if a user completes login, `hasSeenWelcome` is set. If they then log out, `useLogout` (line 164) explicitly **deletes** `hasSeenWelcome` so the welcome screen reappears. This is intentional per the comment on line 161–163.

However, the `useAuth` hook in `_layout.tsx` initializes `setAuth(data.session?.user ?? null)`. If `hasSeenWelcome` is false and the user already has a valid session (e.g., app reopened without logout), they'd briefly see the welcome screen before the routing effect redirects them. The routing guard only redirects on `isNewLogin` (line 121), not on every render — so this isn't a flash issue.

**Verdict:** Working as designed. Document the dual write in the screen doc. No change needed.

## 📋 Moderate

### M1 · Error banner lacks dark-mode styling
**File:** `login.tsx:138–157`

The error banner uses inline styles with `colors.dangerBg` and `colors.danger`. NativeWind class `text-dangerStrong` handles dark mode via `tailwind.config.js` tokens. However, the `backgroundColor` is hardcoded via inline style (`colors.dangerBg`) — if `dangerBg` is `#FEF2F2` in both light and dark, it won't adapt.

**Fix:** Check `theme.ts` `dangerBg` in dark mode. If it's the same light pink in dark, the error banner will mismatch dark-mode surface. Either add a dark variant token or use NativeWind `bg-dangerBg dark:bg-dangerBg-dark` if dark tokens exist.

### M2 · AuthHeader uses NativeWind class `text-[28px]` — token misalignment
**File:** `src/components/ui/AuthHeader.tsx:12`

Uses hardcoded `text-[28px]` instead of `typography.h2` or similar token. The 28px was chosen to match the header title spec, but this bypasses the typography system.

**Fix:** Reference `typography.h2` or similar token. Also consider `font-bold` → should be "800" (ExtraBold) per the flow doc spec.

### M3 · AuthDivider uses `text-textMuted` — `textMuted` not in all theme tokens
**File:** `src/components/ui/AuthDivider.tsx:8`

`text-textMuted` references a Tailwind class that maps to `colors.muted` token. Verify `colors.muted` exists in both light and dark token sets in `theme.ts`.

### M4 · No email auto-complete / keyboard return key configured
**File:** `login.tsx:67–74`

Email field doesn't set `returnKeyType="next"` and the password field doesn't set `returnKeyType="go"`. Users have to manually tap each field.

**Fix:** Add `returnKeyType="next"` on email with `onSubmitEditing` focusing password. Add `returnKeyType="go"` on password that triggers `handleSubmit`.

### M5 · No password autofill hint on iOS/Android
**File:** `login.tsx:79–107`

`TextInput` doesn't set `textContentType` (iOS) or `autoComplete` (Android) for email/password. Users won't get native password manager suggestions.

**Fix:** Add `textContentType="emailAddress"` on email, `textContentType="password"` on password. Add `autoComplete="email"` / `autoComplete="password"`.

## 🔧 Low / Minor

### m1 · Inline `StyleSheet.create` not used — styles scattered between inline and NativeWind
**File:** `login.tsx`

The screen uses a mix of NativeWind classes (`className="..."`) and inline `style={}` props. Example: the error banner (line 138–157) uses both approaches in the same component. For consistency, prefer NativeWind for layout and static visuals, inline styles only for dynamic values.

### m2 · Back button behavior when entry point is welcome screen
**File:** `login.tsx:43–49`

The back button always calls `router.back()`. If the user navigates from signup to login (signup has a back + "Sign In" link), `router.back()` goes to signup. If from welcome screen, goes back to welcome. Both are correct. No fix needed — document for awareness.

### m3 · Typography token `typography.caption` used for field labels (13px)
**File:** `login.tsx:64,76`

Field labels use `typography.caption`. The spec (flow doc) calls for "13px semibold". Verify `typography.caption` is exactly 13px in the theme token.

### m4 · ArrowLeft icon hardcodes `strokeWidth={2}`
**File:** `login.tsx:48`

Minor inconsistency — other icons in the codebase may use default stroke. No impact, purely stylistic.

### m5 · `hitSlop` on password toggle doesn't account for icon container
**File:** `login.tsx:89`

The `hitSlop` is on the `TouchableOpacity` itself, which is fine. But the `Eye`/`EyeOff` icon is wrapped in a `View` inside `Input` component (line 167–169: `<View className="ml-2">{icon}</View>`). The actual tappable area is only the icon size (20dp) plus hitSlop. With `marginLeft: 8` from the View, the touch target shifts right. This is fine for usability.
